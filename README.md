# Real-Time Fraud Detection System

A real-time fraud detection system built with **Python, PyTorch, Apache Kafka, Docker, Streamlit, and SHAP**.

The project demonstrates an end-to-end machine learning pipeline that simulates financial transactions, streams them through Apache Kafka, evaluates transaction risk using a deep learning model, generates SHAP-based explanations, and presents the results through an interactive Streamlit dashboard.

> **Disclaimer:** This is an educational and portfolio project. It uses the PaySim synthetic financial transaction dataset and simulated transaction streaming. It is not intended to be used as a production banking or financial fraud detection system.

---

## Project Overview

Financial fraud detection requires more than simply predicting whether a transaction is fraudulent.

A useful fraud detection workflow should be able to:

- Process transactions continuously
- Identify potentially fraudulent transactions
- Handle highly imbalanced fraud data
- Provide explanations for model predictions
- Allow human reviewers to investigate flagged transactions
- Monitor detection results through a dashboard

This project combines machine learning with event streaming to demonstrate such a workflow.

Key Features
1. Deep Learning Fraud Detection

A neural network built with PyTorch is used to classify transactions as potentially fraudulent or legitimate.

The model uses engineered transaction features and outputs a fraud probability.

2. Real-Time Transaction Streaming

Apache Kafka is used to simulate a real-time transaction processing environment.

Transactions generated by the transaction generator are published to Kafka and consumed by the machine learning service.

3. Explainable AI with SHAP

SHAP is used to explain model predictions by identifying which transaction features contributed to the predicted fraud risk.

This makes the prediction easier to investigate instead of treating the model as a black box.

4. Human-in-the-Loop Fraud Review

The system is designed around a fraud operations workflow where model predictions support human investigation.

The model identifies potentially suspicious transactions while the dashboard provides information that can be reviewed by a human operator.

5. Streamlit Dashboard

A Streamlit dashboard provides a visual interface for monitoring:

Incoming transactions
Fraud predictions
Fraud probability
Model explanations
Transaction statistics
Detection results
6. Dockerized Services

The major components are containerized using Docker and Docker Compose.

This allows the streaming and machine learning components to run as separate services.

Handling Class Imbalance

Fraud detection datasets are typically highly imbalanced.

In this dataset:

Legitimate transactions: 6,354,407
Fraudulent transactions:     8,213

Training a model without addressing this imbalance could result in a model that performs well on the majority class while failing to detect fraudulent transactions.

To address this, the training process uses a weighted binary classification loss.

The calculated positive-class weight is approximately:

773.748

This gives fraudulent examples substantially greater importance during model training.

Model Evaluation

Because fraud detection is a highly imbalanced classification problem, accuracy alone is not a sufficient evaluation metric.

The project evaluates the model using:

Precision
Recall
F1 Score
False Negatives
Number of Flagged Transactions
Detection Threshold: 0.50

Using a fraud probability threshold of 0.50:

Metric	Result
Precision	0.0886
Recall	0.9854
F1 Score	0.1625
False Negatives	24
Flagged Transactions	18,280

At this threshold, the model identifies a very high proportion of the fraudulent examples, while also flagging a substantial number of transactions for further investigation.

Detection Threshold: 0.70

Using a fraud probability threshold of 0.70:

Metric	Result
Precision	0.1818
Recall	0.9610
F1 Score	0.3058
False Negatives	64
Flagged Transactions	8,683

The threshold demonstrates the trade-off between detecting more suspicious transactions and reducing the number of transactions sent for investigation.

The appropriate threshold would depend on the operational requirements and acceptable false-positive/false-negative trade-offs of a real fraud detection environment.

Explainable AI

The system uses SHAP (SHapley Additive exPlanations) to provide explanations for individual predictions.

Instead of displaying only:

The project uses a tree-based SHAP explainer where applicable and supports fallback explanation approaches depending on the model/explanation workflow.

This approach recognizes that a fraud detection model can assist analysts by prioritizing suspicious transactions while human reviewers can investigate the available transaction information and model explanation.

Why Kafka?

Kafka provides an event-streaming layer between transaction generation and machine learning inference.

Without Kafka:

Generator ─────────► ML Model

With Kafka:

Generator
    │
    ▼
 Kafka
    │
    ▼
ML Consumer

This separation makes the architecture more representative of a distributed streaming application and allows the producer and consumer to operate independently.

Why SHAP?

A fraud detection model may identify a transaction as suspicious, but the probability alone does not explain the prediction.

SHAP provides feature-level contribution information that can help answer:

"Which features contributed to this prediction?"

This is particularly useful in a human-review workflow where an analyst needs additional context when investigating a flagged transaction.

Limitations

This project has several limitations.

Synthetic Data

The PaySim dataset is synthetic and does not represent real banking transactions.

Class Imbalance

The dataset contains very few fraudulent transactions compared with legitimate transactions.

This makes precision/recall trade-offs particularly important.

Model Generalization

Performance on the PaySim dataset should not be interpreted as performance on real-world financial transactions.

Simulated Streaming

Kafka streaming is simulated using generated transactions rather than a real banking transaction source.

Threshold Selection

The fraud classification threshold affects the balance between detecting fraudulent transactions and generating false positives.

A real deployment would require threshold calibration based on operational requirements and validation data.
